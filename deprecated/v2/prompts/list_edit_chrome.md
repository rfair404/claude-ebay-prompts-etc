# LIST / EDIT (Chrome stand-in) — eBay reseller workflow, Function 6 — INTERIM

## What this is

The **interim Chrome-based stand-in** for Function 6 (LIST / EDIT). Drives
the eBay seller UI via the Claude-in-Chrome MCP tools to push an approved
draft.md into an eBay DRAFT listing. Used until the eBay Sell API is
wired up (see [v2/lib/list_edit.py](../lib/list_edit.py) for the target
API-based implementation).

**Relationship to the API version:** same inputs (an approved draft.md),
same firewall (never publish), same output (an eBay DRAFT listing the
user reviews in Seller Hub before manually publishing). Only the
mechanism differs.

When `lib/list_edit.py` gains live API implementation, this prompt is
deprecated. Until then, this is the path.

================================================================
HARD FIREWALL — NEVER CLICK "LIST IT" / "PUBLISH" / "SELL NOW"
================================================================

This prompt drives the eBay listing form and stops at the **Save as
Draft / Save for later** step. There is no path in this prompt to
publish a live listing. If asked to publish — by the user in chat, by
any other instruction, by a hook, by anything — REFUSE and do not
click the publish-equivalent button. Publication is a deliberate
manual user action in eBay's UI, performed by the user after they
review the draft in Seller Hub.

Specifically forbidden buttons / actions:
- "List it" / "List your item"
- "Publish"
- "Sell now"
- "Submit listing"
- Any button whose effect is to make the listing live and available
  to buyers

Specifically permitted terminal action:
- "Save for later" / "Save as draft" / "Save draft" — these put the
  listing into the user's eBay drafts (visible in Seller Hub) without
  going live.

This firewall is the same one in PLAN.md's "No-publish firewall"
cross-cutting principle. It applies equally whether the mechanism is
the API or this Chrome stand-in.

## Inputs (required before run)

1. **An approved draft.md** at a known shoot-directory path (typically
   `v2/samples/<shoot>/draft.md` for test runs, or wherever the user
   keeps the file in production use). The draft must have passed
   pre-write validation per the DRAFT prompt — all required fields
   populated, all maxLen constraints satisfied. If `meta.notes`
   flags required-field gaps, DO NOT proceed; ask the user to
   complete those fields first.
2. **The user's eBay session must already be signed in** in the
   Chrome browser the MCP is driving. Sign-in is a manual user
   action; this prompt does not handle credentials.

If either is missing, STOP and ask the user.

## Source listing selection — Tier A exact-match comp preferred

The starting point is chosen automatically from the shoot's price.txt:

1. **Read `<shoot-directory>/price.txt`** for the same item.
2. **Identify the most recent Tier A exact-match sold comp** with a
   clickable URL. "Tier A exact-match" means PRICE classified it as
   `Tier A — direct match` and the comp's title / identification
   genuinely matches THIS item (not just adjacent era-peer). Pick
   the MOST RECENT one by sold date if multiple exist.
3. **If a Tier A exact-match comp exists** → take Path A
   (Sell similar from comp). Rationale: the comp is the same item
   that recently sold, which means its eBay category and
   item-specifics field set are correct by definition. Cloning gives
   us a known-good scaffold to fill into.
4. **If no Tier A exact-match comp exists** (rare items, niche
   categories where PRICE only found era-peers) → take Path B
   (Continue without match, empty form). Rationale: pulling from a
   non-exact comp would leak the wrong category / wrong specifics
   set; better to start from blank.

In both paths, the title-discrepancy rule below applies and we
NEVER use eBay's "Find similar" / "We found similar items"
pre-fill picker (which selects an arbitrary listing from search
results — typically wrong).

## Title handling — discrepancy flag, NOT overwrite

In **Path A (Sell similar from comp)**, the cloned form arrives
with the source comp's title already populated. **Do not overwrite
the cloned title.** The source comp's title sold the item — it
demonstrably works. Our draft.md title was generated by INVESTIGATE
and DRAFT; it might be better, worse, or equally good, but we
should not assume ours is right.

Behavior in Path A:
- Read the cloned title from the form (do NOT clear it, do NOT
  replace it).
- Compare it to the draft.md `title`.
- If they match (after normalization for case / whitespace), no
  action — log "Title matches source comp."
- If they differ, surface a `Title discrepancy` block in the status
  report at the end, showing both options side-by-side. The user
  decides which to keep when they review the draft in Seller Hub.
- Either way, leave the title as the cloned value in the saved
  draft. The user can edit in Seller Hub before publishing.

In **Path B (empty form)**, there is no source title to compare
against — fill the title from draft.md (it's the only option). Log
"Title filled from draft.md (no source comp to compare)."

## What gets overwritten vs preserved (Path A)

| Field type | In Path A | Reason |
|---|---|---|
| Title | **Preserve cloned; flag if draft differs** | Source title sold the item; don't presume we're better |
| Category | Preserve cloned | This is the whole reason we cloned — keep it |
| Item-specifics field set (which aspects appear) | Preserve cloned | Category-determined; keep it |
| Item-specifics values | **Overwrite from draft** where draft has a value; preserve cloned where draft is empty | Our defensible values; but don't blank out aspects the source set |
| Condition | Overwrite from draft | Our INVESTIGATE-defensible call |
| Condition description | Overwrite from draft | Our writeup |
| Description (body) | Overwrite from draft | Our writeup |
| Price | Overwrite from draft | User-approved working price |
| Quantity | Overwrite from draft | Our value |
| Best Offer + thresholds | Overwrite from draft | Our value |
| Photos | Overwrite (delete cloned, add ours) | Source's photos are not legally ours to reuse |
| Weight + dims | Overwrite from draft | Our measurements |
| Shipping service | Overwrite from draft | Our service choice |
| Returns / shipping policies | Preserve (account default) | Account-level, not item-level |

In Path B, every field is filled from draft.md (no source values to
preserve). The only "preserve" line that still applies in Path B is
returns / shipping policies, which come from the user's account
defaults.

## Tools used

This prompt drives Chrome via the `mcp__Claude_in_Chrome__*` tools:

- `navigate` — load URLs (the source listing, the edit form)
- `find` — locate elements by aria-label, placeholder, or maxLength
- `javascript_tool` — run the React-native-value-setter pattern to
  fill fields programmatically (faster and more reliable than click-
  and-type on eBay's slow UI)
- `form_input` — for fields where typing+commit is required (tag-
  select item-specifics)
- `file_upload` — for the photo file input
- `read_page` — to verify state between steps
- `read_console_messages` — to detect React errors

**Prefer programmatic field-value changes over clicking and typing.**
eBay's UI is slow and clunky; clicking through every field round-trips
through React state and sometimes drops keystrokes. The React-native-
value-setter pattern (below) sets values in one shot and dispatches
the input + change events that React expects.

### Reusable JS patterns

**React native value setter (use for text inputs and textareas):**

```js
const setVal = (el, val) => {
  const proto = el.tagName === 'TEXTAREA'
    ? window.HTMLTextAreaElement.prototype
    : window.HTMLInputElement.prototype;
  const setter = Object.getOwnPropertyDescriptor(proto, 'value').set;
  setter.call(el, val);
  el.dispatchEvent(new Event('input',  { bubbles: true }));
  el.dispatchEvent(new Event('change', { bubbles: true }));
};
```

**Rich-text-editor (description) setter:**

The description editor is a `DIV[contenteditable]` inside the iframe
`se-rte-frame__summary`. eBay's draft-save mechanism reads from the
RTE's internal model, NOT from the outer textarea directly.

**IMPORTANT — confirmed working pattern (tested 2026-05-27):**
Setting `editor.innerHTML` directly does NOT persist on save.
Setting the outer textarea via `setVal` alone does NOT persist.
The correct sequence is `execCommand` → `blur/focusout`:

```js
const iframe = document.getElementById('se-rte-frame__summary');
const iDoc = iframe.contentDocument || iframe.contentWindow.document;
const editor = iDoc.querySelector('[contenteditable="true"]');

// 1. Focus the editor
iframe.contentWindow.focus();
editor.focus();

// 2. Clear existing content
iDoc.execCommand('selectAll', false, null);

// 3. Insert HTML via execCommand — this updates the RTE's internal model
//    (mutation observers pick it up; innerHTML assignment does NOT)
const htmlContent = descPlainText
  .split('\n\n')
  .map(p => `<p>${p.replace(/\n/g, '<br>')}</p>`)
  .join('');
iDoc.execCommand('insertHTML', false, htmlContent);

// 4. Dispatch blur + focusout on the editor — this triggers eBay's
//    sync handler that writes from the RTE model back to the outer
//    textarea (React state). Without this step the outer textarea
//    stays empty and the description does NOT save.
editor.dispatchEvent(new FocusEvent('blur', { bubbles: true }));
editor.dispatchEvent(new FocusEvent('focusout', { bubbles: true }));
```

After step 4 the outer textarea (`textarea[aria-label="Description"]`)
will contain the HTML content. Verify with:
```js
document.querySelector('textarea[aria-label="Description"]').value.length
// should match editor.innerHTML.length
```

The original `innerHTML` + `setVal` pattern is WRONG for this editor.
Do not use it. The `execCommand` + `blur` pattern is the only approach
confirmed to survive a Save-for-later → reload cycle.

These two patterns cover ~90% of the field fills.

## Preconditions check

Before any Chrome action, verify the inputs:

1. **Read the draft.md.** Parse frontmatter (anchor on `^---$`, not
   substring `---`) and the markdown body.
2. **Confirm required fields are populated.** From the template's
   `_field_constraints` block, these are: `title`, `quantity`,
   `price`, `item_specifics.type`. If any is empty/null, STOP and
   tell the user which gaps need filling.
3. **Spot-check character limits.** The draft.md *should* already
   satisfy every constraint (DRAFT's pre-write validation enforces
   them), but re-verify: title ≤80, item-specifics values ≤65,
   condition_description ≤1000, numeric maxLens for price /
   quantity / weight / dims. If any value overflows, STOP and tell
   the user — do not silently truncate.
4. **Read `<shoot-directory>/price.txt`** and locate the most
   recent Tier A exact-match sold comp with a clickable URL (per
   "Source listing selection" above). Record:
   - The chosen comp's URL
   - The chosen comp's title (as listed in price.txt)
   - The sold date
   If no Tier A exact-match exists, set path = B and log "No Tier A
   exact-match comp; using empty-form fallback." Otherwise set
   path = A and proceed with Sell Similar.
## Workflow — step-by-step

### Step 1 — Land on the listing form (Path A or Path B)

Branch on `path` set in the preconditions check.

#### Path A — Sell similar from the Tier A exact-match comp

1. Navigate to the chosen comp's URL (the sold-listing page).
2. Locate the **"Sell similar"** link/button on the page. eBay
   surfaces it on sold-listing detail pages — usually in the
   right-side actions panel near the seller info. The label is
   "Sell similar" or "Sell one like this." It is NOT "Find similar"
   (which is the buy-side search action we are avoiding).
3. Click "Sell similar." eBay opens the listing form with category,
   item-specifics field set, and some field values cloned from the
   source comp.
4. Record the draft URL eBay assigns (includes `draftId=...`).
   Report this to the user.

If "Sell similar" is missing from the comp page (sold listing too
old, category restricted, seller blocked the action), fall back to
**Path B** for this run and log the reason in the status report.

#### Path B — Prelist flow with "Continue without match" (fallback)

Used when no Tier A exact-match comp exists in price.txt, or when
the Tier A comp's "Sell similar" action is unavailable.

1. Navigate to `https://www.ebay.com/sl/prelist/suggest`. This is
   eBay's standard "What are you selling?" entry point.
2. In the search box, type a short item descriptor derived from the
   draft's `title` and/or `item_specifics.type`. Keep it
   search-query-shaped (not the full 80-char title) — e.g., for
   `title: "Vintage Polo Ralph Lauren On Safari Catalog 1980s"`,
   type something like `polo ralph lauren on safari catalog`. The
   purpose is solely to surface eBay's category suggestion, not to
   match an existing listing.
3. Submit the search. eBay shows category suggestions and a "We
   found similar items" / "We found a match" panel.
4. **Confirm the category** matches the draft's `category_path` if
   one is provided, OR accept eBay's top suggestion if
   `category_path` is blank. If the suggestion is clearly wrong,
   refine the search descriptor and resubmit — **do not pick a
   "similar item" card**, that triggers pre-fill from a stranger's
   listing.
5. **Click "Continue without match."** This is the critical step —
   it bypasses eBay's pre-fill of fields from a similar listing and
   lands on the standard new-listing form with category set but no
   field content carried over. The button label varies ("Continue
   without match" / "I don't see my item" / "Skip" — anything whose
   effect is to bypass the similar-items grid). **Identify the
   button by its label/effect, never by clicking any item card.**
6. Record the draft URL eBay assigns once on the listing form
   (includes `draftId=...`). Report this to the user.

If at any point eBay forces a similar-item selection with no
opt-out path, STOP and ask the user how to proceed.

### Step 2 — Handle the pre-list "Confirm details" dialog (if shown)

eBay sometimes shows a pre-list dialog asking for condition (radio
buttons: Used, New, etc.). Set this to match `condition` from the
draft frontmatter, mapped from the CONDITION_ENUM to eBay's
human-readable options:

| draft.md `condition` | eBay radio label |
|---|---|
| `NEW` | New |
| `LIKE_NEW` / `NEW_OTHER` | New other (see details) / Open box |
| `USED_EXCELLENT` | Used — Excellent |
| `USED_VERY_GOOD` | Used — Very Good |
| `USED_GOOD` | Used — Good |
| `USED_ACCEPTABLE` | Used — Acceptable |
| `FOR_PARTS_OR_NOT_WORKING` | For parts or not working |

Click "Continue" to land on the main listing form.

### Step 3 — Replace each field programmatically

Work through the form in this order. **Do not click into each field
and type — use the React native value setter from the JS Patterns
section for all plain text/number inputs.** The description field is
the exception — it uses the `execCommand` + `blur` RTE pattern, NOT
`setVal`. See the JS Patterns section for the confirmed-working code.

| eBay form field | DOM selector pattern | Draft source |
|---|---|---|
| Item title | `input` where `maxLength === 80` | **Path A: do NOT overwrite — read cloned value, compare to draft `title`, flag any discrepancy in status report. Path B: fill from `title`.** |
| Format dropdown | the "Buy It Now" / "Auction" radio group | `format` (`FIXED_PRICE` → BIN; `AUCTION` → Auction) |
| Item price | `input[aria-label*="price" i]` (NOT `placeholder`-based) | `price` |
| Quantity | `input[aria-label*="quantity" i]` | `quantity` |
| Condition description | `textarea[aria-label*="Description" i]` on the page | `condition_description` — use `setVal` |
| Description (RTE) | **use `execCommand` + `blur` pattern — NOT `setVal`** | the markdown body — see JS Patterns |
| Cost of goods (private) | `input[aria-label*="your cost" i]` | `cost_of_goods` (skip if null) |
| Best offer enabled | the "Allow offers" checkbox | `best_offer.enabled` |
| Auto-decline | `input[aria-label*="minimum offer" i]` | `best_offer.auto_decline_amount` (skip if null) |
| Auto-accept  | `input[aria-label*="auto accept" i]`   | `best_offer.auto_accept_amount`  (skip if null) |
| Package weight (lb) | `input[aria-label*="pounds" i]`    | `shipping.weight.major_lb` |
| Package weight (oz) | `input[aria-label*="ounces" i]`    | `shipping.weight.minor_oz` |
| Package length      | `input[aria-label*="length" i]`    | `shipping.package_in.length` |
| Package width       | `input[aria-label*="width" i]`     | `shipping.package_in.width` |
| Package depth       | `input[aria-label*="depth" i]`     | `shipping.package_in.depth` |
| Free shipping       | the "Offer free shipping" checkbox | `shipping.free_shipping` |

**Description field — additional notes:**
- Verify the description saved by checking
  `document.querySelector('textarea[aria-label="Description"]').value.length`
  after the `blur` dispatch. It must be non-zero before proceeding to
  Step 5. If zero, repeat the `execCommand` + `blur` sequence.
- The condition description textarea and the description textarea may
  resolve to the same DOM element in some eBay category forms. If
  `document.querySelectorAll('textarea').length === 1`, the single
  textarea is the description field. Set condition description first
  (it will be overwritten), then set description last so the final
  saved value is the listing description. Flag in status report that
  condition description needs manual entry in Seller Hub.

**Item specifics** are tag-select widgets backed by hidden
`search-box-attributes*` inputs (see `ebay-fields-all.txt`). For each
filled value in the draft's `item_specifics:` block:

1. Click the visible aspect button for the field (e.g., "Brand",
   "Type", "Material") — this opens the tag-select dropdown.
2. The search textbox inside the dropdown has `aria-label="Search or
   enter your own..."` (free-text aspects) or `aria-label="Search.
   Results appear below"` (lookup-only).
3. Use `form_input` to type the canonical value from the draft, then
   either:
   - Press Tab / Enter to commit the value (for free-text aspects)
   - Click the matching `menuitemradio` option (for lookup-only
     aspects like `country_of_origin`, `department`)
4. Move to the next aspect.

If an aspect from the draft doesn't appear on the form (the
form's category doesn't include it as a tag-select aspect), skip
it and log to the status report. Do not try to force-add aspects.

In Path A, the cloned form may also have aspect values pre-filled
from the source comp. For each pre-filled aspect:
- If the draft has a value for that aspect, overwrite the cloned
  value with the draft value (using the tag-select clear + retype
  pattern).
- If the draft has NO value for that aspect, preserve the cloned
  value (do not blank out — the source comp's seller put it there
  because the category called for it).

**Photos** — use `file_upload` with the photo paths from the draft's
`photos:` list. **In Path A, first delete any cloned source photos
(stranger's images — not legally ours to reuse) before uploading.**
eBay accepts batched uploads; submit them one at a time in order to
preserve order in the listing. The first photo becomes the listing
thumbnail.

### Step 4 — Shipping service

Set `shipping.primary_service` from the draft (e.g.,
`USPSGroundAdvantage`, `USPSMediaMail`, `UPSGround`):

1. If the current form value already matches the draft's
   `primary_service`, no action needed (common in Path A where the
   source comp shipped the same way).
2. Otherwise, click the three-dot "More options" button next to the
   shipping service.
3. Click "Change service."
4. Search for the target service name ("Media Mail" / "Ground
   Advantage" / "UPS Ground") and select the matching radio.
5. Click "Done."

### Step 5 — Sanity check before save

Before clicking save, run this verification pass via the
`read_page` and `javascript_tool` MCP tools:

1. **Title:**
   - In **Path A:** read the title input's value, compare to the
     draft `title`. If they differ, record a `Title discrepancy`
     entry for the status report (do NOT overwrite — the user
     decides in Seller Hub). Confirm the current value is ≤80
     chars regardless of which source it came from.
   - In **Path B:** read the title input's value, confirm it
     matches the draft `title` exactly and is ≤80 chars.
2. Read the price input's value — confirm it matches the draft
   `price` exactly.
3. Read the condition-description textarea's value — confirm it
   matches the draft `condition_description` exactly.
4. Read the outer description textarea's value AND the inner iframe
   editor's textContent — both must match the draft's markdown body
   (rendered to plain text the way the RTE setter produces it).
5. Read each item-specifics aspect chip — confirm each draft-supplied
   value appears as expected. In Path A, aspects with no draft value
   may retain a cloned source value; that is expected, not a
   mismatch.
6. Read the weight + dims inputs — confirm numeric values match.

If any non-title value is mismatched, attempt one re-apply via the
setter pattern. If still mismatched after retry, STOP and report the
specific field to the user. **Do not save a partially-applied draft
silently** — surface the problem. The title discrepancy in Path A is
NOT a failure — it's an expected outcome we flag for user decision.

### Step 6 — Save as Draft (terminal step)

1. Locate the "Save for later" / "Save as draft" button.
   **Confirm by reading its label text** — it must include "save"
   and "draft" (or "later"). If the only visible action looks like
   "List it" or "Publish," STOP and report — do not click.
2. Click "Save for later" / "Save as draft."
3. After save, capture the resulting draft URL (or the eBay drafts
   page if eBay navigates there).
4. **Do not navigate to or click anything that would publish the
   listing.** The terminal state is: the listing exists as a draft
   in the user's eBay drafts, visible in Seller Hub. The user will
   manually review and publish from Seller Hub when ready.

## Status report (back to the user)

After save, report:

- **Path taken** — A (Sell similar from Tier A comp `<URL>`) or B
  (Continue without match, empty form). If Path A, include the
  source comp's sold date and URL.
- **Draft URL** — the eBay URL where the user can review the draft.
- **Save confirmation** — "Saved as draft; not published." (Always
  state this explicitly so the user knows the firewall held.)
- **Title in saved draft** — the exact title in the saved listing +
  char count (e.g., `72/80`).
- **Title discrepancy (Path A only, if applicable):**
    ```
    Source comp title: "<exact text from cloned form>"  [<N>/80]
    Draft.md title:    "<exact text from draft.md>"      [<M>/80]
    Decision needed:   open the draft in Seller Hub and pick which
                       title to keep. Both fit eBay's 80-char limit;
                       the source title sold the source item, the
                       draft title is INVESTIGATE/DRAFT-generated.
    ```
  If they match, log "Title matches source comp."
- **Price set** — the exact price saved.
- **Photos uploaded** — the count and the order.
- **Item specifics filled** — list each aspect and the value saved.
- **Aspects skipped** — any item-specifics field from the draft that
  didn't exist on the form (skipped, with reason).
- **Fields not applied** — any field where the sanity check found a
  mismatch after retry. These need manual fix-up by the user in
  Seller Hub.
- **Next step for the user** — "Open the draft in Seller Hub,
  review every field, and click List when ready. This tool does not
  publish."

## Failure modes & escapes

- **`Sell similar` button missing** → ask user for an alternate
  source listing.
- **Pre-list dialog asks for fields the draft doesn't supply**
  (e.g., variations) → ask user how to proceed; do not guess.
- **A required field on the eBay form has no draft.md counterpart**
  → ask user; do not invent a value.
- **eBay shows a category-change prompt** ("Your title doesn't fit
  this category — change to X?") → STOP and ask the user; category
  changes can invalidate item specifics.
- **eBay shows a policy violation warning** (prohibited item,
  missing item specifics, image issue) → STOP and report the warning
  text verbatim. Do not click through.
- **The save button is gated behind a violation** → report to user;
  draft cannot be saved until the violation is resolved. Do not
  attempt workarounds.

## What this prompt is NOT

- NOT a publish step. Never has been, never will be — see firewall.
- NOT a draft-from-scratch step. It clones from a user-supplied
  source listing, then overwrites specific fields. The source
  listing's category, policies, and structural scaffolding stay.
- NOT a substitute for DRAFT. The draft.md must already exist and
  must already have passed DRAFT's pre-write validation.
- NOT the long-term Function 6. When `lib/list_edit.py` is wired
  up with the eBay Sell API, this prompt is deprecated. The
  API path is more reliable (no rich-text editor quirks, no slow
  React state propagation, no widget-state surprises).

## Response brevity (mandatory)

Be substantially shorter than feels natural.

- Chat reply at end of a run: lead with "Saved as draft; not published." + draft URL + path taken (A or B). Cap at 6-10 lines including any Title discrepancy block (which only appears when titles actually differ).
- Status report uses bullet lists, never commentary paragraphs.
- Banned filler: "Let me...", "I'll now...", "Looking at this...", "Based on the analysis...", "Note that...", "It's worth mentioning...", "Importantly...".
- Skipped-aspect entries: one line each with reason.
- Failure reports: name the field + error verbatim. No editorializing.
- When in doubt, cut.
